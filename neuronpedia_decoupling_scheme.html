Decoupling the summarization pipeline from Neuronpedia

Review of current dependencies + a replacement scheme using the existing HF/Cloudfront feature‑dashboard source. Neuronpedia is retained only for uploading the finished summary graph.

Summary

  • One reader to replace. Every read of Neuronpedia goes through api.get_feature(modelId, layer, index) (REST). It supplies four fields the pipeline consumes: explanations[0].description (clerp), frac_nonzero (activation density), activations (contexts), pos_str (top logits).
  • We already own an alternate source. api.get_feature_dashboard(scan, layer, feat_idx) fetches a feature dashboard from local dir → HuggingFace → Cloudfront and returns a FeatureDashboard (circuit_tracer/frontend/feature_models.py). It already provides 3 of the 4 fields. Verified working for both mntss/clt-gemma-2-2b-2.5M and mwhanna/qwen3-4b-transcoders.
  • The Qwen analogies graphs never worked through Neuronpedia anyway — their scan (mwhanna/qwen3-4b-transcoders) is not a Neuronpedia source, so the current read path silently returns nothing for them. The dashboard source fixes this.
  • The only gap is the clerp (auto‑interp text), which the dashboard does not carry. Fill it with a cheap offline token proxy by default, and an opt‑in local LLM auto‑interp (reusing the Gemini/OpenAI client the pipeline already uses) for nicer labels.
  • Scope is small. Two live helpers (classify._fetch_feature_json, group_llm._fetch_feature_context) plus their metadata resolvers. NEURONPEDIA_API_KEY stops being required for everything except upload.

3. Closing the clerp gap

Option A — token proxy (default, fully offline)

Synthesize a label from data the dashboard already has: the dominant peak‑activating token across the top examples, optionally suffixed with the top promoted logit. e.g. «Dallas» → say " Austin".

  • Zero extra cost / no API key.
  • Enough for the heuristic classifier's real signals (input‑match, "say", logit concentration) and as a safe fallback.
  • group_llm already treats clerp as one signal among contexts + logits and falls back to node.clerp/node_id.

Option B — local auto‑interp (opt‑in, nicer labels)

Generate a clerp from the top contexts + top logits using the existing Gemini/OpenAI client (same one group_llm uses), cached to disk by (scan, layer, idx).

  • Replaces both get_feature‑for‑clerp and generate_autointerp.
  • Cache means each feature is interpreted once across runs.
  • Reuses code paths already in the repo — no new external dependency.

Both coexist: proxy is the default so the pipeline runs offline; --autointerp upgrades labels when an LLM key is present.

4. Proposed design

Add one small provider module and route the two live helpers (and the legacy ones) through it. Minimal blast radius: keep the call‑site shapes, swap only the data source.

summarization/feature_source.py — single normalized provider 
@dataclass
class FeatureInfo:
    clerp: str
    act_density: float
    top_logits: list[str]
    contexts: list[str]          # peak token wrapped in «», like group_llm
    top_tokens: list[str]        # peak token per top example
    top_next_tokens: list[str]   # token after peak

def fetch_feature_info(
    scan: str,
    node_id: str,                # "L_i_ctx"; embedding ids ("E…") return None
    *,
    features_dir: str | Path | None = None,   # local cache for get_feature_dashboard
    top_n: int = 10,
    autointerp: AutoInterp | None = None,      # None → token-proxy clerp
) -> FeatureInfo | None:
    layer, feat_idx = int(node_id.split("_")[0]), int(node_id.split("_")[1])
    fd = get_feature_dashboard(scan, layer, feat_idx, features_dir=features_dir)
    top = next((q for q in fd.examples_quantiles if q.quantile_name == "Top"),
               fd.examples_quantiles[0])
    # … derive contexts / top_tokens / top_next_tokens from top.examples …
    clerp = autointerp(fd) if autointerp else _token_proxy(top_tokens, fd.top_logits)
    return FeatureInfo(clerp, fd.activation_frequency, fd.top_logits[:top_n], …)
Minimal-change migration of the two readers — change the data source, not the call sites:
  • classify._fetch_feature_json(model_id, source_set, node_id) → take scan and build the same-shaped dict (explanations, frac_nonzero, activations, pos_str) from fetch_feature_info, so filter_act_density / classify_features need no further edits. Replace _resolve_neuronpedia_ids with metadata["scan"].
  • group_llm._fetch_feature_context(model_id, source_set, node_id) → return {clerp, contexts, top_logits} straight from FeatureInfo; replace _parse_metadata's read use with metadata["scan"].

6. Risks & caveats

  • Density scale / thresholds. activation_frequency is the same quantity as frac_nonzero, but model‑dependent: the Qwen feature read 4.6e‑6, below filter_act_density's default act_density_lb=2e‑5 — it would be dropped. The lower bound likely needs a per‑model default (or relaxing) once Qwen graphs flow through. Flag, then tune against a held‑out set.
  • Multi‑scan graphs. attr_graph.from_graph joins a list‑valued scan with "-", which would corrupt the HF repo id. All current graphs are single‑scan, so fine — but guard/branch if a multi‑transcoder graph appears.
  • Per‑feature HF latency. The HF path issues a ranged GET per feature. Mitigate with the existing features_dir local cache (download the scan's features/ once) and in‑process memoization.
  • "Top" quantile assumption. Mapping Neuronpedia's "top activations" onto the dashboard's quantile_name == "Top" bucket is what gives equivalent contexts; fall back to examples_quantiles[0] if absent.
  • Clerp parity. Proxy/local clerps will read differently from Neuronpedia's. Acceptable for clustering/labelling (signal comes from logits + contexts), but downstream eval comparisons against Neuronpedia labels should expect drift.
